\section{Board Representation (\texttt{board.pl})}
\label{sec:board}

\subsection{Data Structure}

The board is represented as a \textbf{list of lists} in Prolog.
Each element of the outer list is a row of the board; each element
of a row is an atom indicating the contents of the square:

\begin{itemize}
  \item \texttt{'.'} --- free (empty) square
  \item \texttt{x}   --- Player~1's pawn
  \item \texttt{o}   --- Player~2's pawn
  \item \texttt{'\#'} --- permanently removed square
\end{itemize}

Positions are represented as the compound term \texttt{Row/Column}
(zero-based indexing). For example, \texttt{2/3} denotes row~2,
column~3.

\textbf{Advantage of this representation:} lists are Prolog's native
data structure, and predicates such as \texttt{nth0/3} (index-based access) and
\texttt{maplist/2} (functional application) are available in the
standard library, greatly simplifying the code.

\subsection{Main Predicates}

The predicate \texttt{initial\_board/2} creates a board of size
$N{\times}N$ entirely filled with free squares:

\begin{lstlisting}[language=Prolog,
    caption={Initial board creation},
    label={lst:initial_board},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
initial_board(Size, Board) :-
    length(Board, Size),        % Board has Size rows
    maplist(make_row(Size), Board). % each row has Size columns

make_row(Size, Row) :-
    length(Row, Size),
    maplist(=('.'), Row).       % each cell is '.'
\end{lstlisting}

\textbf{How it works:} \texttt{length(Board,~Size)} creates a list of
\texttt{Size} uninstantiated variables. \texttt{maplist} applies
\texttt{make\_row} to each element, and within each row, \texttt{maplist(=('.'),~Row)}
unifies each cell with the atom \texttt{'.'}.

Cell updates are \textbf{non-destructive}: Prolog does not modify
existing structures, but constructs a new version of the board.
This is a fundamental characteristic of logic programming.

\begin{lstlisting}[language=Prolog,
    caption={Non-destructive cell update},
    label={lst:set_cell},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
set_cell(Board, Row, Col, Value, NewBoard) :-
    nth0(Row, Board, OldRow, RestRows),   % extract row Row
    nth0(Col, OldRow, _, RestCols),       % extract element Col
    nth0(Col, NewRow, Value, RestCols),   % rebuild row with new value
    nth0(Row, NewBoard, NewRow, RestRows).% rebuild board
\end{lstlisting}

\textbf{Analogy:} consider a film frame. When a character moves,
the previous frame is not erased --- a new frame is created with
the character in the new position. Prolog operates in the same way.

\section{Game Rules (\texttt{rules.pl})}
\label{sec:rules}

\subsection{Move Validation}

A move is valid if the destination square:
\begin{enumerate}
  \item is exactly one step away (in any of the 8 directions);
  \item is within the board boundaries;
  \item is free (\texttt{'.'}).
\end{enumerate}

\begin{lstlisting}[language=Prolog,
    caption={Move validation},
    label={lst:valid_move},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
valid_move(Board, FromR, FromC, ToR, ToC) :-
    board_size(Board, Size),
    Max is Size - 1,
    member(DR, [-1, 0, 1]),     % row delta: -1, 0 or +1
    member(DC, [-1, 0, 1]),     % column delta: -1, 0 or +1
    \+ (DR =:= 0, DC =:= 0),   % cannot stay in place
    ToR is FromR + DR,
    ToC is FromC + DC,
    ToR >= 0, ToR =< Max,       % within boundaries
    ToC >= 0, ToC =< Max,
    get_cell(Board, ToR, ToC, '.'). % free square
\end{lstlisting}

This predicate functions both as a \textbf{verifier} (when
\texttt{ToR/ToC} are already instantiated) and as a \textbf{generator} (when
they are unbound, Prolog generates all combinations of
\texttt{DR/DC} through \textit{backtracking}). This duality is one of the
most elegant features of Prolog.

\subsection{Move Application and Square Removal}

\begin{lstlisting}[language=Prolog,
    caption={Apply a move and remove a square},
    label={lst:apply_move},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
% Move the pawn from From to To
apply_move(Board, FromR, FromC, ToR, ToC, NewBoard) :-
    get_cell(Board, FromR, FromC, Piece),  % read the symbol
    set_cell(Board, FromR, FromC, '.', B1),% clear origin
    set_cell(B1, ToR, ToC, Piece, NewBoard).% place at destination

% Mark a square as permanently removed
apply_remove(Board, Row, Col, NewBoard) :-
    set_cell(Board, Row, Col, '#', NewBoard).
\end{lstlisting}

\subsection{End-Game Condition}

The game ends when the player whose turn it is has no valid move:

\begin{lstlisting}[language=Prolog,
    caption={End-game detection},
    label={lst:game_over},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
game_over(Board, Player, P1Pos, P2Pos) :-
    player_pos(Player, P1Pos, P2Pos, CR/CC),
    \+ valid_move(Board, CR, CC, _, _).
    % \+ means negation: true if valid_move FAILS
\end{lstlisting}

The operator \texttt{\textbackslash+} is Prolog's \textbf{negation as failure}:
``\texttt{\textbackslash+~Goal}'' is true if and only if \texttt{Goal} fails.
Here, \texttt{game\_over} is true when no valid move exists.

\section{Artificial Intelligence (\texttt{ai.pl})}
\label{sec:ai}

\subsection{The Minimax Principle}
\label{subsec:minimax}

\subsubsection{Concept and Analogy}

\textit{Minimax} is the classical algorithm for two-player games with
perfect information~\cite{russell2020artificial}.

\textbf{Analogy:} consider playing chess and deciding the best move.
One reasons: ``If I play here, my opponent will respond with their best
move, then I will respond with mine, and so on.'' The \textit{minimax}
algorithm formalises exactly this reasoning.

\subsubsection{Operation}

The algorithm mentally constructs a \textbf{game tree}:

\begin{itemize}
  \item \textbf{MAX nodes} (Player~1, symbol \texttt{x}): chooses the
        move that \textbf{maximises} the score.
  \item \textbf{MIN nodes} (Player~2, symbol \texttt{o}): chooses the
        move that \textbf{minimises} the score (disadvantaging Player~1).
  \item \textbf{Leaf nodes} (depth~0 or game over): the position is
        evaluated by a heuristic function.
\end{itemize}

\begin{figure}[htbp]
  \centering
  \begin{verbatim}
               MAX [3]
              /        \
         MIN [3]       MIN [2]
        /      \       /      \
      [3]    [12]   [8]    [2]
  \end{verbatim}
  \caption{Example of a minimax tree with 2 levels.
           The MAX player selects the branch with the maximum value;
           the MIN player selects the branch with the minimum value.
           The value at the root is 3.}
  \label{fig:minimax_tree}
\end{figure}

\begin{lstlisting}[language=Prolog,
    caption={Pure minimax implementation},
    label={lst:minimax},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
% Base case 1: depth exhausted -> static evaluation
minimax(Board, _Player, P1Pos, P2Pos, 0, Value) :-
    !, evaluate(Board, P1Pos, P2Pos, Value).

% Base case 2: player has no moves -> terminal loss
minimax(Board, Player, P1Pos, P2Pos, _D, Value) :-
    player_pos(Player, P1Pos, P2Pos, CR/CC),
    \+ valid_move(Board, CR, CC, _, _), !,
    terminal_value(Player, Value).

% Recursive case: generate children and apply max/min
minimax(Board, Player, P1Pos, P2Pos, Depth, Value) :-
    all_move_pairs(Board, Player, P1Pos, P2Pos, Pairs),
    NextD is Depth - 1,
    Other is 3 - Player,        % 1->2, 2->1
    maplist(minimax_child(Board, Player, Other,
                          P1Pos, P2Pos, NextD),
            Pairs, ChildValues),
    ( Player =:= 1
    -> max_list(ChildValues, Value)  % MAX selects the highest
    ;  min_list(ChildValues, Value)  % MIN selects the lowest
    ).
\end{lstlisting}

\subsubsection{Terminal Values}

When a player runs out of moves, the game terminates:

\begin{lstlisting}[language=Prolog,
    caption={Terminal values},
    label={lst:terminal},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
terminal_value(1, -1000). % Player 1 trapped -> loss (negative)
terminal_value(2,  1000). % Player 2 trapped -> P1 wins (positive)
\end{lstlisting}

The values $\pm1000$ are intentionally much larger than any
heuristic evaluation value, ensuring that an actual win or loss
is always preferred over a state with a favourable heuristic.

\subsection{The Alpha-Beta Algorithm}
\label{subsec:alphabeta}

\subsubsection{Concept and Analogy}

\textit{Minimax} is correct but slow: it explores every node in the tree.
\textit{Alpha-beta} is an optimisation that discards branches that
\textbf{can never influence the final result}, without altering the
computed value.

\textbf{Analogy:} imagine selecting the best restaurant from a list.
One has already visited a restaurant rated 8/10. Upon visiting the
second restaurant, a dish rated 3/10 is encountered. Without examining
the rest of the menu, one can conclude that this restaurant will never be
the best option. \textbf{The remainder of the visit can be skipped.}
Alpha-beta applies exactly this reasoning to branches of the game tree.

\subsubsection{The Parameters $\alpha$ and $\beta$}

\begin{itemize}
  \item $\alpha$ (\textit{alpha}) --- the best value the MAX player
        has already guaranteed. Initialised to $-\infty$.
  \item $\beta$ (\textit{beta}) --- the best value the MIN player
        has already guaranteed. Initialised to $+\infty$.
  \item \textbf{Beta cutoff} (at a MAX node): if the current value $\geq \beta$,
        the MIN player would never choose this branch. Search can stop.
  \item \textbf{Alpha cutoff} (at a MIN node): if the current value $\leq \alpha$,
        the MAX player would never choose this branch. Search can stop.
\end{itemize}

\begin{figure}[htbp]
  \centering
  \begin{verbatim}
                MAX [3]
               /        \
          MIN [3]       MIN [?]
         /      \       /      \
       [3]    [12]   [2]   PRUNED
                     ^
          Alpha = 3, this MIN node already has 2.
          Since 2 < 3 (alpha), MAX would never
          choose this path.
          The remaining children are pruned.
  \end{verbatim}
  \caption{Alpha cutoff: the MAX player has already guaranteed the value~3
           (left branch). In the right branch, the MIN node found 2,
           which is worse for MAX. The remaining children of the right
           branch are discarded.}
  \label{fig:alphabeta_cutoff}
\end{figure}

\subsubsection{Implementation}

\begin{lstlisting}[language=Prolog,
    caption={Alpha-beta search --- recursive case},
    label={lst:alphabeta},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
alphabeta(Board, Player, P1Pos, P2Pos, Depth, Alpha, Beta,
          Value, BM, BR) :-
    all_move_pairs(Board, Player, P1Pos, P2Pos, Pairs),
    order_pairs(Pairs, Board, Player, P1Pos, P2Pos, Ordered),
    NextDepth is Depth - 1,
    Other is 3 - Player,
    ( Player =:= 1
    ->  ab_max(Ordered, Board, Other, P1Pos, P2Pos,
               Player, NextDepth, Alpha, Beta,
               -10000, none, none, Value, BM, BR)
    ;   ab_min(Ordered, Board, Other, P1Pos, P2Pos,
               Player, NextDepth, Alpha, Beta,
               10000, none, none, Value, BM, BR)
    ).

% MAX node: update alpha and cut if alpha >= beta
ab_max([move(MPos,RPos)|Rest], Board, Other, P1Pos, P2Pos,
       CurPlayer, Depth, Alpha, Beta, BestVal, BestM, BestR,
       Val, BM, BR) :-
    apply_pair(Board, CurPlayer, P1Pos, P2Pos, MPos, RPos,
               NewBoard, NewP1, NewP2),
    alphabeta(NewBoard, Other, NewP1, NewP2, Depth,
              Alpha, Beta, ChildVal, _, _),
    ( (BestM = none ; ChildVal > BestVal)
    ->  NewBest = ChildVal, NewBM = MPos, NewBR = RPos
    ;   NewBest = BestVal, NewBM = BestM, NewBR = BestR
    ),
    NewAlpha is max(Alpha, NewBest),
    ( NewAlpha >= Beta
    ->  Val = NewBest, BM = NewBM, BR = NewBR  % beta cutoff
    ;   ab_max(Rest, Board, Other, P1Pos, P2Pos,
               CurPlayer, Depth, NewAlpha, Beta,
               NewBest, NewBM, NewBR, Val, BM, BR)
    ).
\end{lstlisting}

\subsubsection{Performance Gain}

Alpha-beta pruning drastically reduces the number of evaluated nodes~\cite{knuth1975analysis}:

\begin{table}[htbp]
  \caption{Complexity: minimax vs.\ alpha-beta}
  \label{tab:complexity}
  \centering
  \begin{tabular}{lll}
    \toprule
    \textbf{Algorithm} & \textbf{Complexity} & \textbf{Nodes (b=8, d=4)} \\
    \midrule
    Pure minimax      & $O(b^d)$      & $8^4 = 4{,}096$ \\
    Ideal alpha-beta  & $O(b^{d/2})$  & $8^2 = 64$ \\
    \bottomrule
  \end{tabular}
\end{table}

In practice, given that each move has on average~8 possible destinations
and 34 removable squares on an initial 6{\texttimes}6 board,
the actual branching factor is $\approx 102$ (see
Chapter~\ref{chap:eval}). Alpha-beta with good move ordering reduces this
factor to $\approx \sqrt{102} \approx 10$ per level.

\subsection{Move Ordering}
\label{subsec:ordering}

The effectiveness of alpha-beta pruning depends strongly on the order
in which moves are evaluated. Evaluating the most promising moves first
maximises the number of cutoffs.

\textbf{Implemented heuristic:}
\begin{itemize}
  \item \textbf{Central moves first}: squares near the centre of the
        board offer more future options (greater mobility).
  \item \textbf{Removals close to the opponent first}: removing squares
        adjacent to the opponent reduces their mobility more rapidly.
\end{itemize}

\begin{lstlisting}[language=Prolog,
    caption={Scoring function for move ordering},
    label={lst:ordering},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
score_pair(Center, OppR, OppC,
           move(MR/MC, RR/RC),
           Score-move(MR/MC, RR/RC)) :-
    MDR is abs(MR - Center), MDC is abs(MC - Center),
    MoveScore is MDR + MDC,    % lower = more central
    RDR is abs(RR - OppR), RDC is abs(RC - OppC),
    RemScore is RDR + RDC,     % lower = closer to opponent
    Score is MoveScore * 3 - RemScore. % weight: move > removal
\end{lstlisting}

\subsection{Evaluation Function}
\label{subsec:eval_func}

When the search reaches the maximum depth without the game having
ended, it is necessary to heuristically evaluate the current position.

\textbf{Two criteria were selected:}

\begin{enumerate}
  \item \textbf{Mobility} --- the number of legal moves available.
        A player with more moves has greater freedom and is further from
        being isolated. This criterion carries a weight of~10.
  \item \textbf{Centrality} --- how close the pawn is to the centre
        of the board. The centre offers more escape directions.
        This criterion serves as a tiebreaker.
\end{enumerate}

\begin{lstlisting}[language=Prolog,
    caption={Heuristic evaluation function},
    label={lst:evaluate},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
evaluate(Board, P1Pos, P2Pos, Value) :-
    P1Pos = P1R/P1C, P2Pos = P2R/P2C,
    valid_moves(Board, P1R, P1C, M1), length(M1, S1), % P1 mobility
    valid_moves(Board, P2R, P2C, M2), length(M2, S2), % P2 mobility
    board_size(Board, Size),
    Center is (Size - 1) / 2.0,
    centrality(P1R, P1C, Center, Cent1),
    centrality(P2R, P2C, Center, Cent2),
    Value is (S1 - S2) * 10 + (Cent1 - Cent2).
    % positive = good for P1; negative = good for P2
\end{lstlisting}

\textbf{Practical example:} on a 3{\texttimes}3 board with P1 at corner (0,0)
and P2 at centre (1,1), the calculation is:
\begin{itemize}
  \item P1 mobility = 2 moves (confined to the corner)
  \item P2 mobility = 7 moves (centre, maximum freedom)
  \item Mobility difference: $(2-7) \times 10 = -50$
  \item Centrality: $(0+0) - (1+1) = -2$ (P2 is closer to the centre)
  \item Total score: $-50 + (-2) = -52$
\end{itemize}
The negative value indicates that P2 holds a clear advantage --- which is
correct: P2 at the centre enjoys considerably greater freedom.

\textbf{Justification:} mobility is the most direct indicator of how close a
player is to being isolated. Centrality captures the strategic tendency of
maintaining the pawn near the centre of the board.

\section{Game Interface (\texttt{game.pl})}
\label{sec:game_loop}

\subsection{Program Flow}

The game follows the flow described below:

\begin{enumerate}
  \item \texttt{play/0} --- displays the main menu.
  \item \texttt{main\_menu/0} --- allows the game mode to be selected
        (human-human, human-AI, AI-AI).
  \item \texttt{setup\_game/2} --- configures the board size and the
        AI search depth.
  \item \texttt{start\_game/4} --- creates the initial board with pawns
        at opposite corners.
  \item \texttt{game\_loop/6} --- main loop: displays the board,
        checks for game over, and executes the current player's turn.
\end{enumerate}

\begin{lstlisting}[language=Prolog,
    caption={Main game loop},
    label={lst:game_loop},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
game_loop(Board, Turn, P1Pos, P2Pos, Mode, Depth) :-
    display_game(Board, Turn),
    ( game_over(Board, Turn, P1Pos, P2Pos)
    ->  Winner is 3 - Turn,  % the opponent won
        announce_winner(Winner, Board),
        play_again
    ;   execute_turn(Board, Turn, P1Pos, P2Pos,
                     Mode, Depth,
                     NewBoard, NewP1, NewP2),
        NextTurn is 3 - Turn,  % alternate: 1->2, 2->1
        game_loop(NewBoard, NextTurn, NewP1, NewP2,
                  Mode, Depth)
    ).
\end{lstlisting}

\subsection{Human Turn vs.\ AI Turn}

When the turn belongs to a human player, the program requests
input in the format \texttt{Row/Column.} (with a full stop, since
SWI-Prolog interprets the input as a complete Prolog term):

\begin{verbatim}
Move (row/column, e.g.: 1/2): 1/1.
Remove a square (row/column): 2/2.
\end{verbatim}

When the turn belongs to the AI, the predicate \texttt{best\_move/7}
is invoked automatically, executing the alpha-beta search and returning
the optimal (move, removal) pair.

\section{Use of Artificial Intelligence in Development}
\label{sec:ai_usage}

Throughout the development of this project, generative AI
(specifically the Claude model by Anthropic) was used extensively and
integrally across all phases of the work. Its use was not limited to
code generation, but encompassed the entire learning and development process:

\begin{enumerate}
  \item \textbf{Concept learning:} AI was consulted to understand
        the fundamentals of Prolog (unification,
        \textit{backtracking}, lists, built-in predicates) through
        explanations, examples, and analogies.

  \item \textbf{Algorithm understanding:} the \textit{minimax}
        principle and the \textit{alpha-beta} algorithm were
        explored with AI assistance, which provided step-by-step
        explanations, tree diagrams, and complexity analysis.

  \item \textbf{Exploration of alternatives:} different approaches
        were discussed for board representation
        (list of lists vs.\ hash table), for the evaluation function
        (mobility, centrality, distance between pawns), and for
        move ordering strategies.

  \item \textbf{Code writing and debugging:} AI assisted in
        writing predicates, correcting logical errors
        (including a bug in the value accumulation within the
        alpha-beta procedure), and in formulating the 33 unit tests.

  \item \textbf{Report writing:} AI was used to assist in
        drafting, structuring, and reviewing this document,
        with the objective of producing clear and accessible
        explanations.
\end{enumerate}

In all cases, the use of AI was guided by the pedagogical objectives
of the course: AI served as a learning and productivity tool,
and not as a substitute for understanding the underlying concepts.
