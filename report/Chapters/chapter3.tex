\subsection{Unit Test Example}

To illustrate the structure of the tests, the test that verifies
the number of valid moves from the centre of a 3{\texttimes}3 board is presented:

\begin{lstlisting}[language=Prolog,
    caption={Test: moves from the centre of a 3{\texttimes}3 board},
    label={lst:test_example},
    numbers=left,
    basicstyle=\small\ttfamily,
    frame=single]
:- use_module(library(plunit)).
:- begin_tests(rules).

test(valid_moves_centre_3x3_count) :-
    initial_board(3, B0),
    set_cell(B0, 0, 0, x, B1),
    set_cell(B1, 2, 2, o, Board),
    valid_moves(Board, 1, 1, Moves), % pawn at centre (1,1)
    length(Moves, N),
    assertion(N =:= 7). % 8 directions - 1 (occupied corner)

:- end_tests(rules).
\end{lstlisting}

\section{Performance Benchmarks}
\label{sec:benchmarks}

To evaluate the performance of the alpha-beta algorithm, the
execution times for the first AI move were measured under different
combinations of board size and search depth.
All tests started from the initial game state (pawns at opposite
corners, completely free board).

\subsection{Methodology}

Times were measured using the \texttt{get\_time/1} predicate from
SWI-Prolog (wall-clock time), in the following environment:

\begin{itemize}
  \item Operating system: macOS Darwin 25.3.0 (Apple Silicon)
  \item SWI-Prolog (standard version, no additional optimisations)
  \item Measurement: time to compute the first AI move
        from the initial state
\end{itemize}

\subsection{Results Analysis}

\subsubsection{Actual Branching Factor}

In the initial state of a 6{\texttimes}6 board, Player~1 can:
\begin{itemize}
  \item \textbf{Move} to 3 squares (corner with 3 free neighbours).
  \item \textbf{Remove} any of 34 free squares
        (36 squares $-$ 2 pawns).
\end{itemize}

Total (move, removal) pairs: $3 \times 34 = 102$.

This is the branching factor at level 1. In subsequent moves,
as pawns advance towards the centre, each player may have up to~8
possible destinations, increasing the branching factor further.

\subsubsection{Impact of Depth}

The transition from depth~2 to depth~4 on the 6{\texttimes}6 board
represents an increase from $87~\text{ms}$ to $167{,}619~\text{ms}$ ---
a factor of approximately $\mathbf{1927\times}$. This super-exponential
growth confirms the combinatorial nature of the problem.

Although alpha-beta significantly reduces the number of explored nodes
compared to pure minimax, the high branching factor ($\approx 102$) in the
initial state of a 6{\texttimes}6 board renders depth~4 impractical for
interactive use.

\subsubsection{Consistency of Selected Moves}

It is notable that across all configurations, the AI selected the
same move: moving the pawn from the corner (0,0) to the centre (1,1).
This is consistent with the evaluation function that favours
centrality --- the pawn at position (1,1) of a 3{\texttimes}3 board
can access up to~7 squares, whereas at the corner (0,0) it has only~3.

The difference in the removal choice between depth~2
((1,2) on 3{\texttimes}3) and depth~4 ((4,4) on 6{\texttimes}6)
reflects the deeper lookahead afforded by the greater search depth.

\subsubsection{Heuristic Function Evaluation}

The tests confirmed the expected values of the evaluation function:

\section{Limitations and Future Work}
\label{sec:limitations}

\subsection{Identified Limitations}

\begin{enumerate}
  \item \textbf{Performance on large boards at high depth:}
        The 6{\texttimes}6 + depth~4 combination is prohibitive
        ($\approx 167$~s per move). The high branching factor,
        resulting from the large number of removable squares,
        is the primary cause.

  \item \textbf{Input format:} human players must enter positions
        in the format \texttt{Row/Column.}
        (with a full stop), since the \texttt{read/1} predicate in
        SWI-Prolog expects a complete Prolog term terminated by a full stop.
        This format may cause confusion.

  \item \textbf{Absence of a transposition table:} identical positions
        reached via different paths are re-evaluated.
        A transposition table would reduce redundant computation.

  \item \textbf{No iterative deepening:} the search depth is
        fixed. Iterative deepening (gradually increasing
        the depth up to a time limit) would improve game
        quality within a fixed time budget.
\end{enumerate}

\subsection{Configuration Recommendations}

Based on the experimental results:

\begin{itemize}
  \item For 3{\texttimes}3 boards: depth~4 is appropriate
        (136~ms per move).
  \item For 6{\texttimes}6 boards: depth~2 is the
        recommended compromise (87~ms per move),
        offering a near-instantaneous response.
  \item Depth~6 is not recommended for boards larger
        than 3{\texttimes}3 without additional optimisations.
\end{itemize}

\section{Conclusions}
\label{sec:conclusions}

This work demonstrated that it is possible to implement a complete
strategy game with AI in Prolog in an elegant and effective manner.

\textbf{Objectives achieved:}
\begin{itemize}
  \item Complete implementation of the ISOLA game with all modes
        (human-human, human-AI, AI-AI) and configurable board sizes.
  \item Functional alpha-beta algorithm with move ordering
        and a heuristic evaluation function.
  \item Suite of 33 unit tests, all passing.
  \item Practical understanding of \textit{backtracking}, logic
        programming, and game search algorithms.
\end{itemize}

\textbf{Key findings:}
\begin{itemize}
  \item Prolog allows game rules to be expressed almost
        directly from their natural language description,
        exploiting \textit{backtracking} to automatically generate
        all valid moves.
  \item Alpha-beta is essential to make \textit{minimax}
        practical: without pruning, depth~4 on a 6{\texttimes}6 board
        would be entirely infeasible.
  \item Move ordering is as important as alpha-beta itself:
        evaluating poor moves first drastically reduces
        the effectiveness of the cutoffs.
\end{itemize}
